# Trial 5: A/B after "one check wave per batch" (2026-11-21)

Same leakscan spec as trial 4. A: one session, no smithy. B: smelt plan + warden forced to run
in parallel (6 tasks, chain 01 → 02–05 → 06), workers at `fast`, one batch check at `normal`.

| | A | B | B in trial 4 |
|---|---|---|---|
| Wall time | ~6 min | ~22 min (10 of them setup: skills, plan, warden prep) | ~31 min |
| Tokens | ~127k | ~909k in subagents (build + batch check ~674k, planted check ~235k) | ~1.8M |
| Planted defects | 3/3, 0 false positives | 3/3, 0 false positives | 3/3 |
| Extra true findings | none reported | 1 blocking (the allowlist scans itself, CI fails), ReDoS in the JWT rule, exponential glob backtracking, CI permissions | some |

## Findings

1. The batch check halved B's cost and found real defects A didn't report: it is the part of
   smithy worth paying for (~200k, ~2 min).
2. Parallel workers don't pay on a project one agent builds in minutes: setup alone took longer
   than A's whole run, and each worker costs ~65k however small its task.
3. smelt already recommends building here for a list like this; B was told to use warden anyway.
   Trial 6 measures the recommended flow.
4. Frictions fixed after this trial: `tasks set` respelled `PR:`; `receipt run` with one quoted
   command line under zsh; receipts dirty or stale after a task file was marked done; `pr template`
   failed without a template; fix-item branches came out `feat/`; workers didn't install
   dependencies first; a batch dir was reused; domain nouns routed tasks to strong.
